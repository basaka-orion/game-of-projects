# 愿景对齐与迭代路线图

更新时间：2026-04-18

## 1. 这个项目最初想成为什么

它不是一个“项目管理工具”或“聊天壳子”，而是一个围绕 Boss 运转的个人智能系统：

- 以项目为神经元，对项目做分类、优缺点分析、时代突破判断。
- 以项目之间的突触关系，发现协作、迁移、混种、跨界的新物种机会。
- 以 Boss 为系统北极星，持续理解其偏好、愿景、行为模式与阶段性目标。
- 以 MemPalace 作为长期记忆底层。
- 以 Karpathy 的 LLM Wiki 工作流作为知识编译与查询中层。
- 以 Hermes 风格的学习、技能进化、自动化巡航作为系统演化引擎。

## 2. 当前偏离主线的地方

### 2.1 从“外脑系统”偏成了“功能集合”

项目里已经有不少模块，但它们更多是横向并列，而不是围绕一个清晰的主循环：

`Boss → 项目组合 → 记忆沉淀 → 知识编译 → 自动化学习 → 反哺 Boss 与项目`

这导致页面很多，但核心体验不够集中。

### 2.2 项目分析更像“单卡片查看”，还不是“项目神经网络”

已有项目分类、雷达图、突触图，但缺少一个统一中枢回答：

- 哪些项目是主突破方向？
- 哪些项目适合做连接器？
- 哪些项目应该重构，而不是继续追加？
- 哪些突触最值得优先推进？

### 2.3 Boss 画像已起步，但还没成为全局调度核心

Boss 页面已经能显示偏好和决策历史，但还不够强地约束：

- 项目排序
- 知识采集优先级
- 自动化研究方向
- 代理协作策略

### 2.4 MemPalace / Wiki / Hermes 目前更接近“思路接入”，不是“可验证对齐”

当前实现已经有：

- `mempalace_drawers`、`memory_closet`
- `wiki_sources`、`wiki_pages`、`wiki_lint_issues`
- `skill_evolution`、`scheduled_tasks`、`teams`

但还需要继续补强：

- 更稳定的 ingest → drawer → wiki 编译闭环
- 更高密度的 Boss / 项目 / 对话回写
- 更真实的自动化执行与结果回灌

## 3. 本轮已经落地的优化

### 3.1 把 War Room 升级成“愿景对齐中枢”

这页现在不只负责多角色推演，还会直接告诉你：

- 五条主线的当前对齐度
- 当前系统的长板与短板
- 哪些项目是突破候选、连接候选、需要重构
- 哪些突触最值得优先推进

### 3.2 新增愿景分析逻辑层

新增 `src/lib/vision/alignment.ts`，把项目、Boss、记忆、知识、进化这五条主线收束成统一报告，避免未来继续只做页面而不做主线。

### 3.3 把“主观感受上的偏离”沉淀为仓库内可持续参考

这份文档本身就是为了防止项目下一轮又偏回“功能很多，但北极星很散”。

## 4. 下一阶段建议优先级

### P1：让 Boss 真正成为系统的调度中心

- 强化长期愿景、短期目标、当前焦点的采集与持续更新。
- 让 Boss 画像直接影响项目排序、知识 ingest 和自动化任务生成。

### P1：把项目突触从“可视化”推进到“可执行”

- 不只显示连接，还要生成真正的行动链。
- 把“协作”“迁移”“混种”转成待执行的实验任务。

### P1：稳定 MemPalace → Wiki 的编译闭环

- 降低待编译抽屉堆积。
- 提高每次 ingest 后对双链、索引、日志的维护强度。

### P2：让 Hermes 式进化不只是统计表

- 让技能使用结果回写更完整。
- 让失败模式驱动 prompt / workflow 修补。
- 让定时任务真正成为系统的学习节律。

### P2：把多代理协作推进成“围绕 Boss 的工作台”

- 不只是能创建 Agent。
- 而是要明确：谁负责研究、谁负责整理、谁负责批判、谁负责执行。

## 5. 对外部参考实现的理解

- MemPalace：更强调 verbatim、本地优先、可检索、可分层的长期记忆。
- Karpathy LLM Wiki：重点不是“向量检索”，而是“原始来源 → 编译 Wiki → schema 约束”的持续积累。
- Hermes Agent：重点不是“代理很多”，而是“技能、记忆、自动化、任务结果回灌”的学习闭环。

因此本项目的正确方向不是继续加页面，而是让这三层真的围绕 Boss 和项目主线运转起来。
