# 多维画像接入骨架方案

更新时间：2026-04-19

适用对象：
- `Openbasaka / Game of Projects` 主桌面端
- 外部参考仓库 `basaka-orion/multi-dimension-profiling`

---

## 1. 目标

把 `multi-dimension-profiling` 接入为 **Boss 建模引擎**，而不是一个孤立的测评页面。

接入后的结果必须满足三件事：

1. 测评结果能沉淀为 Openbasaka 当前可消费的 `Boss` 主档。
2. 画像结果会影响对话、知识整理、War Room 推演、团队协作、自动研究方向。
3. 原始测评结果保留为可追溯历史，不和现有 `boss_profile / boss_memory` 冲突。

---

## 2. 总体原则

### 2.1 不做平行系统

不要把外部仓库整体当成一个独立 App 嵌进来。

正确做法：
- 外部仓库负责：题库、测评、量化维度、画像解释框架。
- Openbasaka 负责：Boss 主档、长期记忆、全局调度、项目推演、知识回灌。

### 2.2 保留单一真相源

接入后使用三层真相源：

- `boss_assessment_runs`
  负责保存原始测评结果和归一化结果。
- `boss_profile`
  负责保存“当前生效”的 Boss 运营画像。
- `boss_memory`
  负责保存画像变化带来的可检索洞察和动态偏好。

### 2.3 先让系统吃到结果，再追求测评完整度

优先级应该是：

1. 先接入轻量版测评，完成结果回写。
2. 先让聊天 / WarRoom / 自动化真实消费画像。
3. 再逐步引入深度测评、多智者对话、纵向追踪。

---

## 3. 建议的最终架构

```text
multi-dimension-profiling
  -> 题库 / 行为实验 / 多智者访谈
  -> Profiling Adapter
  -> NormalizedBossProfile
  -> 写入 boss_assessment_runs
  -> 更新 boss_profile / cognitive_profile_json / boss_memory
  -> 全局消费
     -> Openbasaka chat context
     -> Knowledge Query / Wiki 整理
     -> Teams / Agent 协作
     -> War Room / Boss Match
     -> Scheduler / Research / Telegram
```

---

## 4. 最佳落点

### 4.1 主承载位

`BossTab` 作为主入口和主控制台。

原因：
- 这里已经是 Boss 全局画像中心。
- 已经存在“认知操作系统”编辑位。
- 用户自然会把“我是谁、系统怎么理解我”放到这里管理。

推荐在 `BossTab` 新增：
- `多维画像总览`
- `快速测评`
- `深度测评`
- `最近一次画像更新`
- `画像差异对比`
- `影响范围预览`

### 4.2 次入口

`Onboarding` 只放一个 **Quick Profile**。

定位：
- 5 分钟快速画像。
- 只做冷启动，不做完整画像。

不要在 Onboarding 里塞 30 分钟深度测评，否则会严重拉高首次使用门槛。

### 4.3 全局消费位

必须连到以下位置：

- `src/lib/chat/context.ts`
- `src/lib/knowledge/query-engine.ts`
- `src/lib/teams/engine.ts`
- `src/lib/vision/alignment.ts`
- `src/lib/ai/war-room.ts`
- `src/lib/automation/cron-executor.ts`
- `electron/main/cron-engine.ts`
- `electron/main/telegram/handler.ts`

### 4.4 暂不作为主入口的模块

不建议先放在：

- `KnowledgeVaultTab`
- `MemoryTab`
- `xiaobaixiaobai/xiaobai-app`

这些模块适合消费画像，不适合作为画像主档入口。

## 5. 文件骨架

建议新增以下目录和文件：

```text
src/lib/boss/profiling/
  types.ts
  adapter.ts
  service.ts
  mapper.ts
  summary.ts
  effects.ts
  scoring.ts

src/views/SandboxMap/tabs/boss-profiling/
  ProfilingPanel.tsx
  ProfilingRunCard.tsx
  ProfilingDiffCard.tsx
  ProfilingQuickEntry.tsx

docs/
  多维画像接入骨架方案.md
```

### 5.1 文件职责

`types.ts`
- 定义外部结果类型和内部归一化类型。

`adapter.ts`
- 解析外部仓库输出。
- 屏蔽未来题库变动。

`mapper.ts`
- 把外部多维画像映射成 Openbasaka 的 `BossState` 可消费字段。

`summary.ts`
- 生成适合 Prompt 注入的短摘要、长摘要和不同模块的裁剪摘要。

`effects.ts`
- 把画像结果回写到 `boss_profile`、`boss_memory`、`cognitive_profile_json`。

`scoring.ts`
- 让 War Room 和 Boss Match 真正吃到新画像。

`service.ts`
- 对外提供统一入口：
  - 创建测评
  - 保存测评结果
  - 读取最近画像
  - 应用画像
  - 生成差异报告

## 6. 数据库骨架

### 6.1 新增表

建议新增两张表，不破坏现有 `boss_profile` 结构。

#### `boss_assessment_runs`

保存每一次测评的原始结果和归一化结果。

```sql
CREATE TABLE IF NOT EXISTS boss_assessment_runs (
  id TEXT PRIMARY KEY,
  source TEXT NOT NULL DEFAULT 'multi_dimension_profiling',
  profile_version TEXT DEFAULT 'v1',
  mode TEXT NOT NULL CHECK(mode IN ('quick', 'deep', 'dialogue')),
  status TEXT NOT NULL DEFAULT 'completed' CHECK(status IN ('draft', 'running', 'completed', 'failed')),
  title TEXT DEFAULT '',
  raw_result_json TEXT NOT NULL DEFAULT '{}',
  normalized_result_json TEXT NOT NULL DEFAULT '{}',
  summary_json TEXT NOT NULL DEFAULT '{}',
  confidence REAL DEFAULT 0.7,
  created_at TEXT DEFAULT (datetime('now','localtime')),
  updated_at TEXT DEFAULT (datetime('now','localtime'))
);

CREATE INDEX IF NOT EXISTS idx_boss_assessment_runs_created
  ON boss_assessment_runs(created_at DESC);
```

#### `boss_profile_snapshots`

保存每次“应用画像”后的系统生效快照，便于回滚和比较。

```sql
CREATE TABLE IF NOT EXISTS boss_profile_snapshots (
  id TEXT PRIMARY KEY,
  run_id TEXT REFERENCES boss_assessment_runs(id) ON DELETE SET NULL,
  profile_json TEXT NOT NULL DEFAULT '{}',
  diff_json TEXT NOT NULL DEFAULT '{}',
  source TEXT DEFAULT 'profiling_apply',
  created_at TEXT DEFAULT (datetime('now','localtime'))
);

CREATE INDEX IF NOT EXISTS idx_boss_profile_snapshots_created
  ON boss_profile_snapshots(created_at DESC);
```

### 6.2 继续复用的现有表

- `boss_profile`
- `boss_memory`
- `boss_decisions`
- `project_taxonomy`

### 6.3 写入 `boss_profile` 的关键键值

建议把“当前生效画像”写成这些 key：

- `name`
- `interests`
- `hates`
- `cognitive_profile_json`
- `profiling_last_run_id`
- `profiling_summary_json`
- `value_weights_json`
- `strength_profile_json`
- `emotion_profile_json`
- `social_profile_json`
- `aesthetic_profile_json`
- `worldview_profile_json`
- `motivation_profile_json`
- `long_term_vision`
- `current_focus`
- `profile_version`
- `profile_source`

说明：
- 现有消费者继续读旧字段。
- 新消费者优先读 JSON 扩展字段。

## 7. 类型骨架

建议在 `src/lib/boss/profiling/types.ts` 中建立两层类型。

### 7.1 外部结果类型

    explanationPreferences: string[]
    addictiveFormats: string[]

    antiPatterns: string[]
    integrationGoals: string[]

## 8. 映射规则

把外部仓库的维度归一化成 Openbasaka 可用字段。

### 8.1 推荐映射

| 外部维度 | 写入 Openbasaka 的位置 | 用途 |
| --- | --- | --- |
| 认知架构 | `cognitive_profile_json` + `profiling_summary_json` | 决定回答结构和解释方式 |
| 人格结构 | `preferredStyle` `decisionSpeed` `resourceStyle` | 决定沟通方式和行动风格 |
| 情感系统 | `emotion_profile_json` | 决定表达强度、反馈方式 |
| 动机与价值 | `value_weights_json` `long_term_vision` `current_focus` | 决定项目排序和自动研究方向 |
| 社会联结 | `social_profile_json` | 决定团队协作和 Agent 分工 |
| 审美与创造 | `aesthetic_profile_json` `excitementTriggers` `addictiveFormats` | 决定知识呈现方式和创意方向 |
| 世界观与意义 | `worldview_profile_json` `integrationGoals` | 决定长期叙事与认知框架 |
| 品格优势 | `strength_profile_json` | 决定适合的任务和项目姿态 |

### 8.2 必须避免的错误映射

- 不要把所有维度都直接变成 Prompt 长文本。
- 不要把外部量表原始分数直接塞给 LLM。
- 不要让外部仓库产生第二套 Boss 主档。

## 10. 回写效果骨架

`effects.ts` 需要做 4 件事：

### 10.1 更新 `boss_profile`

写入当前系统生效画像：

- `interests`
- `hates`
- `cognitive_profile_json`
- `profiling_summary_json`
- `long_term_vision`
- `current_focus`
- 各种维度 JSON

### 10.2 生成 `boss_memory`

把画像解释成可检索洞察：

示例：
- `pattern`: 更偏向结构化、框架化解释
- `pattern`: 面对高不确定任务时更能容忍探索
- `goal`: 长期: 建立自己的智能系统
- `preference`: 对文明级视角、跨学科连接更有感觉
- `preference`: 不喜欢空话、无证据判断、纯鸡汤表达

### 10.3 更新快照

写入 `boss_profile_snapshots`，支持：

- 比较两次画像差异
- 一键回滚
- 查看“这次画像改变了什么”

### 10.4 生成模块裁剪摘要

至少生成三种摘要：

- `chat_summary`
- `warroom_summary`
- `automation_summary`

## 11. UI 骨架

### 11.1 Onboarding

只加一个轻量入口：

- 按钮：`先做快速画像`
- 时长：3-5 分钟
- 结果：生成一版初始 `NormalizedBossProfile`

不建议在首次启动里加入深度测试。

### 11.2 BossTab

新增一个 `多维画像` 区块，建议顺序如下：

1. 当前画像状态
2. 快速测评入口
3. 深度测评入口
4. 最近一次画像摘要
5. 画像差异卡片
6. 影响范围预览

影响范围预览建议显示：

- 这会影响聊天回答风格
- 这会影响 War Room 的 Boss Match
- 这会影响自动研究主题
- 这会影响团队协作分工

### 11.3 深度测评的 UI 位置

深度测评建议不要塞在单个弹窗里。

推荐做法：
- 从 `BossTab` 点击进入独立面板
- 分 `Quick / Deep / Dialogue` 三种模式

## 12. 全局消费方案

### 12.1 Chat Context

修改 `src/lib/chat/context.ts`：

- 继续保留 `Boss name / interests / riskTolerance`
- 新增 `profiling_summary_json` 的裁剪注入
- 新增 `long_term_vision / current_focus`
- 新增 `value_weights_json` 的摘要版

建议新增：

```ts
renderOperationalBossPrompt(profile: NormalizedBossProfile): string
renderWarRoomBossPrompt(profile: NormalizedBossProfile): string
renderAutomationBossPrompt(profile: NormalizedBossProfile): string
```

### 12.2 Knowledge Query

目前 `query-engine.ts` 已经吃 `cognitivePrompt`。

下一步要增加：
- 资料应该如何组织更容易被 Boss 吸收
- 哪些主题更值得优先推荐
- 哪种答案结构更容易让 Boss 形成行动

### 12.3 Teams / Agents

让画像影响：

- 默认选哪些 Agent
- 哪些 Agent 更适合主讲
- 哪些 Agent 负责批判、整理、执行

示例：
- 高抽象 + 高世界观导向：优先 `strategy / critic / worldview` 风格角色
- 高审美 + 高创造倾向：优先 `creative / synthesis` 风格角色

### 12.4 War Room

当前 `boss_match` 还是纯 LLM 打分。

下一步应该改成：

```text
LLM 评估 + 结构化画像加权
```

建议公式：

```text
boss_match_final =
  llm_boss_match * 0.55 +
  interest_overlap * 0.15 +
  value_alignment * 0.15 +
  strength_fit * 0.10 +
  anti_pattern_penalty * 0.05
```

这样 `Boss匹配` 就不是一句模糊主观判断，而是会被画像真实约束。

### 12.5 自动研究 / 定时任务 / Telegram

现在这些模块主要只读 `interests / hates`。

接入后应升级为读取：

- `recommendedResearchTopics`
- `currentFocus`
- `value_weights_json`
- `profiling_summary_json`

这样自动化任务不再只是“按兴趣搜”，而是“按阶段目标和内核偏好搜”。

## 13. Phase 方案

### Phase 1：最小闭环

目标：
- 先让结果写进系统，并被主对话消费。

实施：
- 新增 `boss_assessment_runs`
- 新增 `boss_profile_snapshots`
- 完成 `types.ts / adapter.ts / service.ts / effects.ts`
- 在 `BossTab` 增加“快速画像”入口
- 修改 `chat/context.ts` 注入画像摘要

完成标志：
- 做完一次快速测评后，聊天回答风格明显变化。

### Phase 2：Boss 真正成为调度中心

目标：
- 让 War Room、Knowledge、Teams 吃到画像。

实施：
- 修改 `war-room.ts`
- 修改 `vision/alignment.ts`
- 修改 `teams/engine.ts`
- 修改 `knowledge/query-engine.ts`

完成标志：
- 同一个项目，在不同 Boss 画像下，`Boss匹配` 和建议方向会变化。

### Phase 3：深度画像与纵向追踪

目标：
- 接入深度题库、多智者对话、画像差异追踪。

实施：
- 引入 `deep` 模式和 `dialogue` 模式
- 生成画像时间线
- 做画像差异比较页
- 增加“阶段变化”解释

完成标志：
- 用户可以看到“过去 30 天我的画像怎样变化”。

### Phase 4：自动化反哺

目标：
- 让系统主动按画像工作。

实施：
- 自动研究按画像生成选题
- Team 编排按画像生成角色组合
- Telegram / XiaoBai 回答风格按画像裁剪

完成标志：
- 系统主动研究和主动建议都更像“为这个 Boss 定制”。

## 15. 验收标准

接入完成后，至少要满足以下验证：

1. 做完一次快速画像后，`boss_assessment_runs` 有记录。
2. `boss_profile` 中出现 `profiling_last_run_id` 和 `profiling_summary_json`。
3. `BossTab` 能看到最近画像摘要。
4. Openbasaka 对话能明显使用新的认知画像。
5. War Room 的 `Boss匹配` 不再只靠 LLM 主观打分。
6. 自动研究任务不再只按 `interests` 走，而会读 `currentFocus` 和画像摘要。

---

## 16. 当前建议

如果只做一件事，优先做这条链：

```text
Quick Profile
  -> adapter normalize
  -> saveAssessmentRun
  -> applyAssessmentRun
  -> update boss_profile / boss_memory
  -> chat/context consume
```

这是最短闭环，也是最快能让整个系统“更像用户自己”的路径。

---

## 17. 最后的判断

`multi-dimension-profiling` 在 Openbasaka 里最合适的角色，不是“画像工具”，而是：

**Boss Modeling Engine**

一旦这么定义，后续所有接入 decisions 都会更清晰：

- 入口在 Boss，不在杂项工具。
- 结果进主档，不进旁支缓存。
- 影响全局，不只影响一个页面。
- 先服务系统调度，再扩展为完整产品。
